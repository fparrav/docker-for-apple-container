# Releasing

How this fork is released: how to tag a release, what the release workflow
does, what the release notes state, how to install a release, and how to run
the manual runtime validation. The release channel is the Git tag: releases
are GitHub Releases of this repository, and users install from the tag.
Nothing is published to a package index
(see [Index publishing is not enabled](#index-publishing-is-not-enabled)).

## Tagging a release

A release is a Git tag matching `v*` pushed to the repository:

```sh
git tag v0.1.0
git push origin v0.1.0
```

Pushing the tag is the only trigger of `.github/workflows/release.yml`; there
is no manual dispatch, no pull request path, and no schedule.

The tag must be a valid PEP 440 version: the package version is derived from
the tag by `hatch-vcs` (`[tool.hatch.version] source = "vcs"` in
`pyproject.toml`). `v0.1.0` builds; a label such as `v0.0.1-spike` fails the
build, because `-spike` is not a valid PEP 440 pre-release label. A tag that
does not parse stops the workflow in the build step; delete it and re-tag if
you made a mistake.

The release workflow accepts two kinds of tag and nothing else:

- **Final**: `vX.Y.Z`. It needs live evidence (see
  [Release evidence](#release-evidence)) and is published as a normal release.
- **Pre-release**: `vX.Y.Zrc1`, `vX.Y.Za1`, `vX.Y.Zb1` or `vX.Y.Z.dev1`. No
  evidence is required, and the release is published as a GitHub pre-release
  whose notes say that live evidence was not required.

Any other tag (`v0.1.0-rc1`, `v0.1.0.post1`, `v0.1.0-spike`) fails the
evidence check in the `checks` job before anything is built.

An untagged commit builds a development version
(`0.1.dev<distance>+<node>`), never a release version, so a build without a
tag cannot be mistaken for a release.

## What the release workflow does

`.github/workflows/release.yml` has four jobs, all on hosted `ubuntu-latest`
runners:

1. `checks` (hosted checks, `contents: read`): the test report for the `unit`
   and `fake` tiers (`scripts/test_report.py --tiers unit,fake`), the
   compatibility matrix schema and coverage tests, the README compatibility
   block check, a byte-compile of the sources, and the release evidence
   verifier (`scripts/verify_release_evidence.py --tag "$TAG"`, with the tag
   passed through the environment).
2. `package` (`needs: checks`, `contents: read`): checks out with full history
   so `hatch-vcs` can derive the version from the tag, builds the sdist and
   wheel once (`python -m build`) and uploads `dist/` as an artifact.
3. `smoke` (`needs: package`, `contents: read`, a matrix on the Python floor
   from `pyproject.toml` and `3.x`): downloads that artifact and runs
   `scripts/verify_wheel.py --dist dist --expect-version "${TAG#v}"`, which
   installs the wheel in a clean virtual environment and checks the `docker`
   entry point, the import location, `docker version` and the message without a
   `container` CLI (the tag reaches the script only through the environment).
4. `release` (`needs: [checks, smoke]`, `contents: write` — the only job with
   write permission): downloads the same artifact without building again,
   generates the release notes, appends the live evidence section, and
   creates the GitHub Release with `softprops/action-gh-release`, attaching
   everything in `dist/`, using the notes as the body and marking pre-release
   tags as pre-releases. The files that were installed and tested are the files
   that are published.

Pull requests and pushes to `main` run the same wheel check in the `wheel` job
of `ci.yml`, without the version expectation. The package supports the Python
floor `requires-python = ">=3.9"`; the unit suite and `verify_wheel.py` were run
under Python 3.9.6 when this check was added and passed.

The release job runs only after the checks and the smoke test pass. It uses GitHub's
job-scoped `GITHUB_TOKEN` with `contents: write` to create the release; it
requires no external credentials or repository secrets. Every job runs only on
hosted runners, and every third-party action is pinned to a full commit SHA.
There is no package index publishing step and no trusted-publishing permission
(see [Index publishing is not enabled](#index-publishing-is-not-enabled)).

## Release notes

The release body is generated by
`scripts/test_report.py --tiers unit,fake --release-notes` and states, in
order:

- the supported Apple `container` release (the value of
  `SUPPORTED_CONTAINER_VERSION` in `src/container_docker_shim/cli.py`),
- one line per test tier, in the order `unit`, `fake`, `live`,
  `conformance`: a tier that ran is stated with its counts
  (`<tier> tier: ran (… passed, … failed, … skipped, … not run)`), a tier
  that did not run is stated as `<tier> tier: not run` — never as passed,
- when a matrix entry claimed a stronger evidence level than the run produced,
  a "Compatibility claims not reached in this run" section listing each
  flagged entry with its claimed and reached level.

Because the release workflow runs only the `unit` and `fake` tiers, the test
lines of every release state that the `live` and `conformance` tiers did not
run: a release never claims Apple runtime or Docker Engine evidence that the
release build did not produce. The live runtime evidence is stated in its own
section, appended after those lines: for a final tag it names the evidence file,
the Apple `container` version, the UTC date and the live counts; for a
pre-release it says that live evidence was not required.

If a release has user-visible breaking changes (the first release renames the
distribution), add a short "Breaking changes" section to the release body on
GitHub after the workflow creates it.

## Release evidence

Hosted runners cannot run the `live` tier, so a final release is gated on a
file that a maintainer produces on a macOS 26 machine and commits. The
sequence for a final release `vX.Y.Z`:

1. Start from a clean tree: `git status --porcelain -- src scripts tests
   pyproject.toml` must print nothing, because the evidence is bound to `HEAD`.
2. With the supported Apple `container` release installed and its apiserver
   running (`container system start`), run
   `python3 scripts/validate-runtime.py --evidence`. It writes
   `docs/evidence/runtime-<version>-<UTC timestamp>.json` only when every live
   test that the sources declare ran and passed. A failed, partial or
   `--skip-live` run writes nothing (`--evidence` with `--skip-live` is a
   usage error).
3. Commit the file (only documentation, workflows and evidence may change after
   it) and push.
4. Tag `vX.Y.Z` and push the tag. The `checks` job runs
   `scripts/verify_release_evidence.py` and fails unless the newest file in
   `docs/evidence/`:
   - records result `passed` with counts that add up and every declared live
     test passed (no failed, skipped or not-run test);
   - names the Apple `container` version in `SUPPORTED_CONTAINER_VERSION`;
   - has the same tree hash as the tagged commit — the sha256 of the git
     identifiers of `src/`, `scripts/`, `tests/` and `pyproject.toml` (schema 2
     of the file), so a change to any of the four after the run invalidates it,
     while README, `docs/`, workflow and evidence commits do not. A file with an
     earlier schema is refused with a message naming both numbers; run
     `validate-runtime.py --evidence` again;
   - is at most 30 days old (`--max-age-days` changes the limit) and not dated
     in the future.

Pre-release tags (`rc`, `a`, `b`, `dev`) skip all of this and are published as
GitHub pre-releases, which is how to test the pipeline without evidence. Until a
first evidence file exists, only pre-releases can be published.

What the evidence does and does not prove: it records that a maintainer ran the
live tier on the supported runtime against this exact code.
**The file is not signed**, and anyone with write access to the repository can
create one, so it is an attestation tied to the code tree, not independent
proof. It also says nothing about Docker Engine conformance, which CI checks
separately.

## Installing a release

The distribution is `docker-for-apple-container-fork` (see `pyproject.toml`),
deliberately different from the upstream `docker-for-apple-container`.
Because nothing is published to a package index, a release is installed from
the tag, not from an index:

```bash
uv tool install --from git+https://github.com/fparrav/docker-for-apple-container@vX.Y.Z \
    docker-for-apple-container-fork
```

or

```bash
pipx install git+https://github.com/fparrav/docker-for-apple-container@vX.Y.Z
```

`uv` takes the source with `--from` and the distribution as the positional
argument, because the repository is named like the upstream project; both
commands install `docker-for-apple-container-fork`, and the executable lands in the tool bin
directory (`~/.local/bin` by default). Users of the upstream package must
uninstall it first (`uv tool uninstall docker-for-apple-container`,
`pipx uninstall docker-for-apple-container`, or `brew uninstall
docker-for-apple-container`); see the README's
[Switching from the upstream package](../README.md#switching-from-the-upstream-package)
section.

## Running the runtime workflow

The `live` tier and `scripts/validate-runtime.py` cannot run on hosted
runners (no virtualization), so full validation of the supported Apple
`container` release is manual, through `.github/workflows/runtime.yml`:

- **Trigger**: `workflow_dispatch` only. Start it from the repository's
  Actions page (select "Runtime", then "Run workflow") or with
  `gh workflow run runtime.yml`. No pull request, push, or schedule path can
  start a run.
- **Protected environment**: the job declares `environment: runtime`. The
  environment must be protected in the repository settings, so every run
  needs maintainer approval before it starts.
- **Repository guard**: the job runs only when
  `github.repository == 'fparrav/docker-for-apple-container'`; a fork of this
  fork cannot schedule it.
- **Runner**: `runs-on: [self-hosted, macOS, runtime-26]` — the owner's
  self-hosted macOS 26 runner, the only place with the virtualization Apple
  `container` needs.
- **Steps**: checkout, set up Python, then
  `python3 scripts/validate-runtime.py --container /opt/homebrew/bin/container
  --output runtime-report.md`, which runs the read-only matrix check against
  the installed candidate and the `live` tier (disposable `shimtest-` objects
  only, never a prune). The `runtime-report.md` artifact is uploaded even
  when the run fails, so a failed validation still leaves a record.

The validator prints a per-entry evidence table
(`id | claimed | apple side | live test`) plus a problem count, and exits
non-zero when an entry is `missing` or a live test failed. If the installed
candidate's version differs from the supported one, the live tier is reported
not run with the reason, never as passed.

### Runner setup and trust rules

The runner must be a macOS 26 machine on Apple silicon with virtualization
enabled, registered as a self-hosted runner of this repository with the
labels `self-hosted`, `macOS`, and `runtime-26`, running the supported Apple
`container` release (Homebrew) with the container system started
(`container system start`).

A self-hosted runner on a public repository is a trust boundary: workflow
code executes on the owner's machine. The mitigations are deliberate, and all
four are required:

- manual `workflow_dispatch` trigger only — no pull request or push path;
- the protected `runtime` environment — every run needs maintainer approval;
- the repository guard — forks of the fork cannot schedule the job;
- read-only permissions, no secrets, pinned actions — the run cannot write to
  the repository or read credentials, and the live tier creates and removes
  only disposable `shimtest-` objects (never a prune).

## CI limitation

Hosted runners cannot run the full validation. In `.github/workflows/ci.yml`
(pull requests and pushes to main), the `conformance` job runs on
`ubuntu-latest` with `SHIM_TIERS=conformance` and
`SHIM_CONFORMANCE_DOCKER=$(which docker)`: its gate probes the runner's real
Docker Engine with `docker info` and never touches the Apple `container`
runtime. That is **container conformance** — it proves the same fixtures
behave the same on a real Docker Engine, and it records the Docker and
Compose versions in the report — but it says nothing about the Apple
`container` runtime. The `live` tier and `scripts/validate-runtime.py` cannot
run on hosted runners at all (no virtualization); the full Apple runtime
checks require the manual protected runner described in
[Running the runtime workflow](#running-the-runtime-workflow). A release is
therefore not advanced on hosted CI alone. See
[Testing](testing.md) for the tier definitions and the report.

## Index publishing is not enabled

The release workflow publishes nothing to a package index: there is no
publishing step or trusted-publishing permission. Its `GITHUB_TOKEN` is
limited to creating a GitHub Release; no external publishing credentials or
repository secrets are configured. The only release channel is the GitHub
Release with the built sdist and wheel.
Do not describe this fork as available from PyPI or any other index.

Enabling index publishing is a deliberate owner decision. Before it happens,
all of the following must be in place:

1. **Owner decision**: the owner explicitly decides to publish, and the edit
   to `release.yml` is made as a deliberate change, not a default.
2. **Name and project identity**: the index project must be owned by the
   owner and must use a name distinct from the upstream
   `docker-for-apple-container`, which belongs to the upstream project. The
   distribution name (currently `docker-for-apple-container-fork`) must be
   reserved or registered under the owner's index account first.
3. **OIDC trusted publisher**: the index must be configured with a trusted
   publisher for this repository and the release workflow (for example, PyPI
   trusted publishing), and the release job must be reviewed for the
   `id-token: write` permission that trusted publishing requires — a
   deliberate change to the workflow's minimal permissions.

Until then, installation is from the tag or a source checkout, as described
in [Installing a release](#installing-a-release).
